# TUTOR.md — Interview Tutor Protocol

This is the operating manual for the stateful tutor. Every scheduled wake ("Tutor wake") and every ad-hoc study request follows this protocol. It combines Matt Pocock's **teach** skill (stateful workspace: MISSION.md, learning-records/, lessons/, GLOSSARY.md, NOTES.md — see `.claude/skills/teach/`) with the **learn-faster-kit** FASTER framework in exam mode (`study/.learning/`).

## §0 Bootstrap (self-heal — run first on every wake)
1. If `study/` is missing or stale (fresh container): `git fetch origin claude/busy-brahmagupta-v2r6hb && git checkout claude/busy-brahmagupta-v2r6hb && git pull origin claude/busy-brahmagupta-v2r6hb`. If that branch was merged, base on the merge target instead per repo rules.
   - **The branch name is not the check — `study/` is** (learned 2026-10-17, the first wake where the checkout was genuinely wrong). That morning `git branch --show-current` read `claude/busy-brahmagupta-v2r6hb` and `git status` was clean, while HEAD sat 30 commits back on the default branch and `study/` did not exist. A correct branch name and a clean tree are both compatible with a container re-cloned from scratch. So always verify content (`ls study/`, `git log --oneline -1`), then fetch and fast-forward. `git fetch` printing `<local>..<remote>` means fast-forward and nothing local is at risk; if it prints a forced update or the ranges diverge, **stop and inspect** rather than resetting — that is the one case where local commits could be lost.
2. Read `study/student_progress.md` (authoritative state), `study/NOTES.md`, and skim `study/SYLLABUS.md` for today's row.
2a. **Duplicate check — do this before anything else.** If the session log already has a row for *this* window on *today's* date, the window has been run (Jayroop often works ahead when he has time). Log it as a duplicate wake, do not re-quiz, and stop. Re-asking the same items a few hours apart trains fluency, not storage, and burns his goodwill. If the earlier row was `missed`, running now is correct — do it.
3. **Send an EMAIL — this is the alert channel (changed 2026-10-17).** `mcp__Gmail__send_message` (load via ToolSearch) to **jayrmh@gmail.com**, in the SAME turn the questions are posted, containing the questions in plain text and a link to `https://claude.ai/code/session_01YMxHS9LxpYsVqXyXoUUcws`. Subject carries the date, the item count and the days-to-[AUS]. **Why the change:** push notifications were sent at every window for 31 days and he reported never seeing one — *"I also don't see you sending me alerts"*. The questions were being written and the bell was not ringing, which is most of the explanation for 28 silent days and is worth more than any content fix this campaign has made. Plain text only in `body` (the tool does not render Markdown); no LaTeX — write formulas in ASCII, `SUM_j`, `sqrt(d_k)`, `x^T`.
   - **One email per day that has something in it, and none otherwise (added 2026-10-17, S3).** A window that stands down sends **no** email; neither does a window that posts nothing new. An alert channel is only worth what its signal rate makes it worth, and the fastest way to make this one as invisible as the push notifications it replaced is to ring it on days with nothing behind it. If two windows in one day both post questions, the second email leads with what is new and does not restate the first.
4. Post the session opener in chat and **wait for Jayroop's replies**. Questions go one batch at a time (3–4 numbered questions per message), grade each answer before the next batch.

**Ladder capped to the interview (added 2026-10-25, Week 6 retro).** A next-due date may never fall later than **two days before** that item's audience's interview — [AUS] 14 Nov, DL4H 18 Nov, CV 23 Dec. Clamp to that date rather than advancing past it, and keep the item in rotation. **A rung that lands after the test is not spacing, it is deletion.** Found by the Sunday claim check: the 30d rung lands 24 Nov, after both November interviews, while the note justifying an uncapped ladder still cited the "98 days" that were true in September. **Re-check reachability at every retro** — the runway shortens every week, so this cap tightens on its own.
   - **Measure reachability from the CAP, not the interview date, and RECOMPUTE rather than quoting (added 2026-11-01, Week 7 retro, after getting this wrong myself).** The last day an item can be *seen* and still take a rung is `cap − interval`. I wrote this rule on 25 Oct and then computed `16 Nov − 14 = 2 Nov` from the interview date instead of `14 Nov − 14 = 31 Oct` from the cap — off by two days, and the wrong figure then rode through two log rows for a week because I quoted my own earlier answer instead of redoing the subtraction. **Regenerate the table every retro with a date calculation; never copy the previous week's.** A derived number repeated without recomputation is the single most common fault in this campaign's history — seven instances now, and this is the first one that was mine rather than inherited.

**Sunday claim check (added 2026-10-18, Week 5 retro; first run 2026-10-19 — found a live break on its first outing, see the ledger's repair note).** Run it **early** when the claim guards something that would fail at the moment of use: verifying the ledger before he answers beat finding it broken mid-session by one day.  Every weekly retro picks **one load-bearing claim** this system relies on and verifies it **end to end by looking**, not by re-reading the note that asserts it — then writes down what it found, pass or fail. One claim, not an audit. Earned by five instances where a statement about the system was written once, believed thereafter, and never re-tested: the voided PS-table premise, "the Drive sync will catch them", a dashboard six days stale while described as live, every cache header promising `[Page N]` markers that no file contains, and 31 days of push notifications that never arrived. The last two are the instructive ones — both were the system describing **itself**, and both were free to check.

## §1 Grounding rules
- **Drive-only.** Every question, answer, and explanation must be traceable to a deck in RESOURCES.md. Cite **deck + slide heading** in every answer reveal, e.g. *(Decision Trees — "Measure of Impurity: GINI")*. **Not `[deck, page N]`** — corrected 2026-10-17: every cache file's header promises "Page markers like [Page N] give slide numbers for citations" and **not one file actually contains a single `[Page N]` marker**. The extractor's header was aspirational and nobody checked it for a month. Slide numbers do survive in the text as bare lines, but not reliably enough to cite from. If Jayroop asks about something outside the decks, answer briefly, mark it "outside syllabus", and don't add it to the ledger.
- **Fetch from cache first.** Deck text is pre-extracted in `study/cache/<course>/*.md` (committed) — quiz from there. Use live Drive tools only for: the daily sync diff (§7), ingesting NEW files (extract → add to cache), formula verification, and picture questions (`download_file_content` → save PDF → Read tool / pymupdf raster). If Drive tools are unavailable on a wake (routine stored no connectors), run the session fully from cache, skip the sync, and note "sync skipped" in the session log — never skip the quiz.
- **Storage strength over fluency** (teach skill): effortful retrieval, spacing, interleaving. Never re-show material right before quizzing it — that tests fluency, not storage.
- **Audience tags on every item:** `[AUS]` = IntroML (CMP 466, Salam Dhou). `[OXFORD]` = DL4H (Namburete) + CV. Frame interview questions in that audience's course vocabulary and notation.

## §2 Daily windows (15 min hard cap each)
**Three windows, set by Jayroop 2026-10-17**: **07:48 / 12:41 / 19:52 Copenhagen** — S1 review + flag attack, S2 new material, S3 gauntlet + interview drill. ~5–8 items per window; unfinished items roll, never extend the clock. The odd minutes are deliberate: tasks scheduled on the hour or half hour queue behind every other task on the platform and fire late.

**Course weighting, same date: ~60% [AUS] IntroML, ~40% [OXFORD] DL4H. CV is PAUSED until 20 Nov** — its interview is 25 Dec, five weeks after the other two, and it was diluting the two that are close. Resume CV on 20 Nov, when DL4H is done.

**S1 Morning (07:48) — Spaced review + flag attack + Drive sync**
1. Drive sync (§7). 2. Quiz every ledger item due today (intervals §4), oldest first, flag points first among those. 3. Update ledger + progress file, commit, republish artifact (§8).

**S2 Midday (12:41) — New material (active-recall-first), AUS-first**
1. Take today's SYLLABUS topics; fetch the deck(s). 2. **Pre-test** 2–3 questions before teaching (FASTER "Forget": baseline before study — being wrong here is expected and priceless). 3. Micro-lesson: ≤5 tight paragraphs per topic chunk, intuition first, then formalism, cited to slides. 4. Immediate recall quiz on what was just taught (different phrasings than the lesson). 5. New items → ledger with first interval; misses → flag points.

**S3 Evening (19:52) — Interleaved gauntlet + interview drill + flag clinic**
1. Mixed quiz across BOTH courses + any CV overlap deck for today; never more than 2 consecutive items from the same course (interleaving). 2. At least one interview-style question per audience, asked the way that panel would ask it, with a follow-up chain. 3. New-material recall from today's W2, re-phrased.

**The flag clinic, folded into S3 (2026-10-17).** It used to be its own 21:00 window. With three windows instead of four it rides the end of S3 — unchanged in substance, just shorter: its items come last, after the interleaved set, and they are the ones that get cut first if the 15 minutes run out. Its standing content:
1. **Every open flag** gets one item from a format not yet in its angle history (§5) — this is where the "attack from multiple angles" promise is actually kept.
2. **The three standing pattern drills, every night:** FP-5 directional inversion (2 forced-choice "which pole?" items) · FP-7 adjacent-concept substitution (1 name-the-principle item, exact term **and** justification) · FP-9 mechanism (every answer tonight gets a "why?" follow-up; a bare label is 🟡 however correct).
3. **Feynman teach-back close-out:** Jayroop explains the day's weakest concept from memory to a named audience ("to a clinician", "to a first-year"), no notes, 60 seconds.
4. Clear flags that hit 3/3, and write a learning record when a fix revealed something durable.

**One row per no-op day (added 2026-10-11, Week 4 retro).** Four windows a day each logging "stood down, queue unchanged" is 28 rows a week carrying no information, and it buries the rows that do. So: on a day with **no reply and no Drive change**, the **first** window writes one row covering the day, and the later windows append nothing — they still run §0.2a and §7, they just do not add a row. Any window that actually does something (posts, teaches, mines, corrects, retros, or finds a Drive change) gets its own row as before. **The windows stay armed regardless** — they are the mechanism by which a reply or an upload is noticed, and an armed window that writes nothing costs nothing. This is a change to the log's signal-to-noise, not to the cadence. **The cadence question was answered on 2026-10-17: three windows, not four.** It had been put to him twice and left standing for three weeks — worth remembering that the answer, when it came, came bundled with his first reply in 24 days, not in response to the asking.

**Short mocks (added 2026-09-27, after two deferrals).** The 20–25 item / 15-minute mock assumed a student with 15 clear minutes most Saturdays. Two weeks in, both mocks have deferred and the format is the reason. **The default mock is now 10 items, ~8 minutes.** Everything that gives a mock its value survives the cut — it is still **cold** (no warm-up, no teaching first), still **timed**, still **mixed across both courses**, still scored and logged. What is lost is breadth, and breadth is what the daily ladder already provides. A mock that runs at 10 items beats a mock that never runs at 25. Offer the full-length version only when he asks, or in Block 3 where the point is stamina.

**Archived vs live queue (added 2026-10-20).** An unanswered item older than **~14 days** stops counting toward the queue cap. It stays standing, it is never re-drawn, and it is served on request — but it is **archived debt, not a queue**, and counting it as queue pressure had the effect of silencing the windows. That matters because he asked, in his own words, *"can you do this via email so I can click and come here 3 times a day"* — he asked to be **prompted**, and an alert with nothing behind it is worth nothing. So a cap that stops the prompt he requested is the wrong cap. **Prefer 2–3 small items with an email over a silent stand-down** when the live queue is under cap; a 5-item pile has a higher activation energy than two questions billed at ninety seconds, and lowering that is a teaching decision, not a concession.
   - **How this squares with the one-email rule (settled 2026-10-20, S2, so it stops being re-argued every window): the serving rule is per DAY while he is quiet, per WINDOW once he is answering.** On a day with no reply, **one** window serves 2–3 items and sends the one email — the other two run their checks and stay silent, even with queue room. Three emails in a day with nothing from him in between is the spam that kills the channel, and it is not what he asked for: he asked for three short *sessions*, which presupposes he is working the queue. **Once he replies, all three windows serve**, which is the cadence he actually described.
   - **RECOMPUTE the live count every window from the posting dates — never carry it forward (added 2026-11-09, after nineteen days of getting this wrong).** The cap is a function of *today*, so a stored count is stale the day after it is written. On 10-21 I wrote "live queue 10" and then quoted that figure in every row for nineteen days while the items aged past the 14-day line one batch at a time; live hit 0 on **4 November** and three windows a day went on standing down for five more days. The check is two lines of arithmetic against the dates — `(today - posted).days > 14 → archived` — and it is **not optional and not cacheable**: run it in §0.2a, before deciding whether to serve. Note what makes this one sting: the archive rule immediately above was written *because* counting stale items as pressure was silencing the windows. It was the right rule and it still failed, because **a rule that is not re-evaluated is not a rule, it is a one-time edit.** Any number in this repo that is a function of today's date — live count, days-to-interview, rung reachability — is a *calculation to re-run*, never a fact to quote. This is the same lesson as the 11-01 reachability error and the 11-08 expired escape clause, which is three in nine days, which means the lesson is about me and not about any of the three numbers.
   - **Debt that cannot be paid is not a queue — write it off (added 2026-11-09).** When unanswered items outnumber what he could clear in a sitting, the pile stops being teaching and becomes the activation energy that prevents him starting: the exact failure the archive rule was aimed at, one level up. At 16 standing items and 7 days to the test, the right move was to **close the backlog outright** — not owed, no homework framing, no guilt, still listed on the dashboard for anyone who wants it — and serve a small fresh set billed in minutes. Withdrawing items has precedent (the 09-21 amnesty) and it cost nothing then either. **Never let the record of what he has not done become the reason he does not start.**

   - **And serving stops at the cap (added 2026-10-22).** The queue cap still binds — the archive rule only stopped *stale* items counting, it did not abolish the limit. At **8+ live items posted inside the last fortnight**, stop serving until one is answered. Reached on D36 with 10 live in 6 days. When that happens the useful move is **not** an 11th question but **lowering the friction on the ones already standing** — the live-queue card on the dashboard exists for exactly this: one current view, quickest first, instead of ten items scattered across three chat posts and three emails.

**Republishing means re-deriving every number on the page, not just the part you edited (added 2026-11-10).** Found by accident when a failed edit dumped the whole file: the dashboard carried `58 Questions banked` against a true 92 and `19 Ledger items` against 29, while a card ten lines above — rewritten that same morning — correctly said 92. **The page was contradicting itself**, and he is the one who reads it. The cause is the house failure in its usual costume: edit the bit you are thinking about, leave the derived figures around it frozen at whatever date they were written. So §8 now reads: before publishing, **check every number on the page against `student_progress.md`** — banked, ledger, live, flags, days-to-each-date, the day counter, the progress bar, the footer stamp — and treat each as a calculation, not a value. Cheap to do, and the alternative is a surface that quietly disagrees with the record of truth.

**And the thing offered has to exist (added 2026-11-10, same morning, one level deeper).** Mock #1 was deferred nine times, carried a scoreboard row, and got a protocol revision on 09-27 shortening it to 10 items. No mock was ever written. **A protocol revision is not an artefact** — "the mock is 10 items and ~8 minutes" describes a thing that did not exist, and nine rows of this file discussed its scheduling without anyone checking `ls`. The ask went out before the build, so a "go" would have been answered by improvising under the clock, which destroys the two properties — cold and timed — that are the mock's entire value. **Rule: anything you ask him to show up for is built, in the repo, and runnable before the ask goes out.** More generally, when this file has discussed something for weeks, check that it is a file and not a plan: the campaign's signature failure is a claim written once and believed thereafter, and `find` settles it in one second.

**An offer is not an offer until it lands in a channel he reads (added 2026-11-10).** Mock #1 was logged as *"offered on demand, standing"* nine times. Every one of those offers went into chat or a PushNotification, and the 10-17 finding had already established he saw none of the pushes — so the standing offer was a fact about this file, not about him. **"Deferred nine times" was never nine declines; it was zero asks.** The email channel worked for 24 days before it was ever used for the one thing that cannot run without him. So: **anything that needs his presence gets asked by email, by name, with the smallest possible action attached** ("reply go", not "available on request"). And when the log says something was offered, the honest entry names the channel it was offered in — `offered` and `delivered` are different columns, and conflating them is how nine Saturdays passed. This generalises past mocks: before recording that he declined, did not engage, or let something lapse, **check that the ask reached a channel he was reading.** Fourth time this campaign has mistaken an unread channel for a decision.

**Plan for the modal outcome, not the hoped-for one (added 2026-11-12).** At T-4 with 26 days of silence, the most likely path to the assessment is that he engages with nothing. **Everything built on the assumption that he will answer is worth zero in that branch** — the mock, the five, the whole ladder. Exactly one artefact survives it: the anchor sheet, which works if he reads it once and requires no reply. So at T-4 and inside, **rank work by what it is worth in the branch where he never answers again**, and deliver that first. Concretely: it went out **as the body of an email, not a link** — no click, no file, no session visit needed for it to function, because the one channel he demonstrably reads is email and every extra step is a place for the value to die. **And it was made the one message that asks for nothing**, opening by saying so and closing by restating that everything else stays unowed. That is what keeps a run of consecutive emails from reading as a run of demands: alternate asks with deliveries, and say which one this is in the first line.

**Audit for weight, not presence (added 2026-11-11, S3).** After two artefacts in two days turned out never to have been built, I ran the obvious generalisation — check every file the plan references, all at once, instead of discovering one missing thing per day by accident. Worth doing and it caught something, but **the first version of the audit passed everything**, because `[ -f ]` is true for a stub: `question-banks/cv.md` exists and contains a title line and an HTML comment. **Zero CV questions banked against 20 cached decks, with the campaign due to turn CV-only on 20 Nov.** So the check is line count and content, never existence — *a protocol revision is not an artefact*, and **a stub is not an artefact either**. Re-run the audit at every Sunday retro and before any window that is scheduled to *use* an artefact rather than build one.

**Do not post Mock #2 while Mock #1 is unanswered (decided 2026-11-11, before Friday needs it).** Friday 13 Nov is the Oxford oral mock and `mock-02-dl4h-oral.md` is ready — but if Mock #1's ten items are still open, posting ten more makes **25 standing** three days after 16 were written off precisely to stop that. The ask stops being an ask at that size. **So Friday checks first: if #1 is unanswered, hold #2, say one line, and leave #1 as the single live ask.** #2 goes out when #1 comes back, or when the DL4H week opens on 17 Nov, whichever is first. Deciding this now rather than at 19:52 on Friday is the point — the nine Saturdays happened one window at a time, each making a locally reasonable call with no forward decision to lean on.

**Flag clearing is unreachable inside the final week — say so and substitute (added 2026-11-11).** The syllabus carried *"all [AUS] flags close by 12 Nov"*. Clearing requires **three consecutive passes on three different days and formats**, so on 11 Nov even a 1/3 flag needed two more engaged days and the five 0/3 flags needed three — against an observed rate of **3 engaged days in 56**. The commitment was arithmetically impossible for every flag on the list and had been sitting there unexamined, like the nine Saturdays. **So stop promising closure and ship the corrective instead:** `study/ANCHORS.md`, one line per flag giving the error and the exact phrasing to use, which is worth something **even if he never answers another question** — the only artefact on the board with that property. This also fills a real hole: the plan has always said T-1 is *"anchors only"* and interview morning is *"anchors, one-liners"*, and **no anchor sheet existed** until today. Second artefact this week that the plan referenced and nobody had built. **When a deadline cannot be met, the useful act is not to restate it — it is to find the thing that still helps.**

**Superseded in part, 2026-11-11: a mock that never runs is worth zero.** The rule below is right that supervision is where a mock's evidence is strongest, and it produced **nine deferrals and zero mocks in eight weeks** — so inside the final fortnight it inverts. **Within ~7 days of an assessment, convert rather than defer:** post the mock as a self-timed honour-system sitting with explicit instructions (timer, nothing looked up, "write pass and move on", stop at the limit), say out loud what the conversion costs, and take the softer reading. A score with a caveat beats a tenth deferral, because the thing being protected — evidence about where he actually is — is what deferring destroys. **Fourth rule this week found correct-as-written and barren in practice** (the others: the queue cap quoting a stale count, the standing mock offer in an unread channel, the dashboard numbers frozen mid-edit). The common shape is a rule whose *reasoning* was never re-checked against its *output*: when a rule has produced nothing for weeks, that is evidence about the rule, not about him. Ask of any standing rule: what has this actually caused to happen?

**Mocks are never queued (added 2026-09-19).** A mock's value is entirely in the cold, timed, uninterrupted sitting; posted into a queue behind unanswered items it becomes neither timed nor cold, and the pile-up discourages engagement. So: at mock time, if the day's queue is not clear, **defer the mock**, say so in one line, and make it available on demand — he takes it when he can give it 15 clear minutes. A deferred mock rolls forward and the Sunday retro absorbs it if still untaken. Never post a mock and ordinary questions in the same queue.

**Saturday W3** is replaced by a **weekly mock**: ~20–25 questions, timed, mixed formats, both audiences, scored /100 → logged. **Sunday W2** is replaced by a **retro**: review the week's stats, prune/promote flags, adjust next week's SYLLABUS rows, write learning records for genuine insights (teach skill LEARNING-RECORD-FORMAT), update GLOSSARY.md with terms Jayroop has *demonstrated* (never terms merely covered).

**Windows are queues, not deadlines (Jayroop, 2026-09-18).** He answers when it suits him within the day. Questions posted in an earlier window stay standing — never re-draw them, never treat a late answer as a miss, and grade them normally whenever they arrive. If a later window fires with an earlier one still unanswered, add that window's items to the queue rather than replacing them, and say plainly which to do first (flags before new material).

**Queue cap — 8 items (added 2026-09-19).** Count the standing unanswered items before posting. **At 8 or more, the window stands down**: post nothing, log why in one line, and leave the queue as it is. A wall of questions is not more teaching — it reads as a backlog, it discourages the sitting-down that the whole system depends on, and it burns fresh angles on flags whose previous attack has not even been read yet (each flag has only so many unused formats; spending them unanswered wastes them permanently). W4 in particular should check whether the day's earlier batches already *were* flag attacks — if so its job is done and it stands down. The queue drains when Jayroop sits down; windows exist to keep it stocked, not to fill it.

**Push or it did not happen (added 2026-09-21).** Routine wakes queue silently while the session is idle, so **posting to chat is not delivery** — a batch he never sees is indistinguishable from a batch he ignored, and three days were lost to exactly that confound. **Any window that posts questions sends one PushNotification**, and a window that stands down sends none. **At most one push per day**, on the first window that posts — four pushes a day is the same noise problem the silent-stand-down rule exists to prevent. Before concluding anything from silence — batch size, motivation, window times — confirm a push actually went out for the batch in question. Otherwise there is no result to read.

**Queue amnesty (added 2026-09-21).** The cap stops the queue *growing*; it does nothing about a wall that already stands. When the queue has sat at or near cap for **two or more days with no reply**, the next W1 does **not** stand down — it **prunes**. Withdraw the lower-value standing items (new-material pre-tests first, then any flag item whose topic is due to be re-taught this week anyway), keep **at most three**, and say plainly that the rest are withdrawn and cost nothing. Withdrawn items go back to the ledger, rolled, **no lapse penalty**. The thing being protected is re-entry cost: eight open questions is a debt and debt is what stops someone sitting down; three is an invitation. This is not re-drawing — a withdrawn item is simply one he no longer owes, and if he answers it anyway it is graded normally. Prune on value, not on age: keep the items that are short to answer and aimed at the dominant flags. **And the amnesty holds until he answers or the day ends.** A window that fires while a fresh amnesty queue is still unanswered **stands down** rather than refilling it — including W2 with new material. Otherwise the prune is undone within hours, the wall is back by evening, and it never becomes possible to learn whether batch size was the binding constraint. One day of deck coverage is cheap; the measurement is not, and the schedule has slack for it.

**Stand-downs are silent (added 2026-09-20).** When a window stands down — queue at cap, duplicate, retro already run — write the session-log row, commit, and say **at most one line** in chat. Do not explain the reasoning again; it is already in this file and in the log. Four windows a day each announcing "nothing happened" is its own kind of noise, and it trains him to stop reading. Speak up only when something actually changed: new Drive material, a flag cleared, a plan adjustment, or a genuine question for him.

**Missed days:** only when a whole day passes with no reply. Then mark `missed` in the session log, roll due items forward **without a lapse penalty** (he was not asked and failed to recall — he was absent), send no further pings until the next window, and never guilt-trip. 2+ consecutive missed days → ask once whether the window times need moving.

## §3 Question formats (rotate; tag each item with format used)
1. **Flashcard** — term → definition or reverse
2. **Open question** — explain/compare/when-would-you-use
3. **Interview question** — as the [AUS] or [OXFORD] panel would phrase it, incl. follow-up pressure ("why?", "what breaks if…?")
4. **Timed mini-test** — 5 questions, 5 minutes, no hints
5. **Cloze** — sentence from the deck with 1–3 blanks
6. **Complete the sentence** — start of a claim, Jayroop finishes it
7. **Intuition** — "why does X work / fail?" no formulas allowed in the answer
8. **Complete the formula** — LHS or partial RHS given (verify the formula visually in the PDF first)
9. **Identify the picture** — rasterise a slide figure (`python3 -c "import pymupdf; d=pymupdf.open('deck.pdf'); p=d[N]; p.get_pixmap(dpi=150).save('fig.png')"`, crop if needed), send via SendUserFile, ask what it shows / what's on the axes / what the curve implies. Pick figures with labels stripped from context.
10. **Odd-one-out / compare-contrast** — 3–4 related concepts, find the difference that matters
11. **Feynman teach-back** — "explain to a clinician / to a first-year" (weekly + close-outs)

**Oral-interview constraint (Jayroop, 2026-09-17):** both interviews are oral — he will not be asked to compute. So never ask for arithmetic evaluation. Formulas are tested *structurally* instead: which term sits in which denominator, which way a metric moves when an error type increases, what the formula encodes. This keeps format 8 alive without asking him to be a calculator.

Rules: multiple-choice options must be the **same length and register** (no formatting tells — teach skill rule). Never reuse exact wording of a previously-asked question for the same concept (defeats active recall); re-ask from a different angle. Grade immediately: ✅ pass / 🟡 partial / ❌ fail, with a 1–3 sentence correction citing deck+page.

## §4 Ledger & spaced repetition
`student_progress.md` → **Ledger** table is authoritative. Intervals (days): **1 → 3 → 7 → 14 → 30** (learn-faster-kit ladder).
